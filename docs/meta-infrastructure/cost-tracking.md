# Cost Tracking

## What it is

Cost tracking for LLM systems is the practice of measuring, attributing, and controlling the token spend generated by every model call — per request, per user, per feature, and per pipeline stage. ("Tokens," roughly words or word-fragments, are the unit model calls are billed and measured in.) It turns "we spent $X on the model API this month" into "feature Y costs $0.04 per user session, user Z has used $12 this week, and the summarization step accounts for 60% of total spend."

Without cost tracking, LLM spend is a black box. You receive a monthly bill and can't answer the basic operational questions: which features are expensive, which users are heavy consumers, whether a model change increased or decreased cost, or whether you're approaching a budget limit.

## The problem it solves

LLM API costs are opaque and can be surprising:

- **Exponential context growth**: each message in a multi-turn conversation is re-sent as part of the context. A 20-turn conversation doesn't cost 20× one message — it can cost 100× due to growing input token counts.
- **Model upgrade cost drift**: upgrading from a cheaper to a more capable model can silently 10× costs on the same traffic.
- **Agentic call amplification**: a single user action that triggers an agent loop with 5 tool calls and 3 model calls can cost 20× a direct model call.
- **Per-user cost inequality**: 1% of users often drive 30–50% of token spend through longer queries, more turns, or heavier feature use.

Cost tracking lets you detect these patterns, set budgets, and route or throttle before spend becomes unacceptable.

## How it works under the hood

### Token counting per call

Every Anthropic API response includes usage metadata: `input_tokens` (what you sent in), `output_tokens` (what the model generated back), and (when prompt caching — reusing precomputed work on a repeated prompt prefix — is active) `cache_creation_input_tokens` (tokens written to the cache on this call) and `cache_read_input_tokens` (tokens reused from an earlier call's cache). These are your source of truth for token spend.

```python
import anthropic

client = anthropic.Anthropic()

PRICING = {
    "claude-sonnet-4-6": {
        "input":        3.00 / 1_000_000,   # $ per token
        "output":      15.00 / 1_000_000,
        "cache_write":  3.75 / 1_000_000,
        "cache_read":   0.30 / 1_000_000,
    },
    "claude-haiku-4-5-20251001": {
        "input":        0.80 / 1_000_000,
        "output":       4.00 / 1_000_000,
        "cache_write":  1.00 / 1_000_000,
        "cache_read":   0.08 / 1_000_000,
    },
}

def cost_usd(usage, model: str) -> float:
    p = PRICING.get(model, PRICING["claude-sonnet-4-6"])
    return (
        usage.input_tokens * p["input"]
        + usage.output_tokens * p["output"]
        + getattr(usage, "cache_creation_input_tokens", 0) * p["cache_write"]
        + getattr(usage, "cache_read_input_tokens", 0) * p["cache_read"]
    )

def tracked_call(messages: list, model: str = "claude-sonnet-4-6", system: str = "") -> dict:
    response = client.messages.create(
        model=model,
        max_tokens=512,
        system=system,
        messages=messages,
    )
    cost = cost_usd(response.usage, model)
    return {
        "response": response.content[0].text,
        "model": model,
        "input_tokens": response.usage.input_tokens,
        "output_tokens": response.usage.output_tokens,
        "cost_usd": cost,
    }
```

Note: pricing changes over time. Store pricing in configuration, not hardcoded constants, so you can update it without a code change.

### Per-feature attribution

Tag every model call with the feature that triggered it. Sum tags in your observability store — wherever you log and monitor what your application is doing — to get per-feature cost breakdown:

```python
from dataclasses import dataclass, field
import uuid
import time

@dataclass
class CostRecord:
    record_id: str = field(default_factory=lambda: str(uuid.uuid4()))
    timestamp: float = field(default_factory=time.time)
    feature: str = ""
    user_id: str = ""
    session_id: str = ""
    model: str = ""
    input_tokens: int = 0
    output_tokens: int = 0
    cost_usd: float = 0.0

_cost_log: list[CostRecord] = []

def attributed_call(
    messages: list,
    feature: str,
    user_id: str = "",
    session_id: str = "",
    model: str = "claude-sonnet-4-6",
) -> dict:
    result = tracked_call(messages, model=model)

    record = CostRecord(
        feature=feature,
        user_id=user_id,
        session_id=session_id,
        model=model,
        input_tokens=result["input_tokens"],
        output_tokens=result["output_tokens"],
        cost_usd=result["cost_usd"],
    )
    _cost_log.append(record)

    return result

def cost_by_feature() -> dict:
    totals: dict[str, float] = {}
    for record in _cost_log:
        totals[record.feature] = totals.get(record.feature, 0.0) + record.cost_usd
    return dict(sorted(totals.items(), key=lambda x: x[1], reverse=True))

def cost_by_user() -> dict:
    totals: dict[str, float] = {}
    for record in _cost_log:
        totals[record.user_id] = totals.get(record.user_id, 0.0) + record.cost_usd
    return dict(sorted(totals.items(), key=lambda x: x[1], reverse=True))
```

### Budget guardrails

Enforce per-user and per-session spending limits to prevent runaway costs from a single user or session:

```python
import threading

# WARNING: This implementation uses in-memory state.
# It does NOT work correctly in production: spend is lost on restart,
# and it does not synchronize across multiple app instances.
# For production, back this with Redis (INCRBYFLOAT with TTL) or a database.
class BudgetGuard:
    def __init__(self, user_daily_limit_usd: float = 1.0, session_limit_usd: float = 0.25):
        self.user_daily_limit = user_daily_limit_usd
        self.session_limit = session_limit_usd
        self._user_spend: dict[str, float] = {}
        self._session_spend: dict[str, float] = {}
        self._lock = threading.Lock()

    def check_and_record(self, user_id: str, session_id: str, cost: float) -> tuple[bool, str]:
        with self._lock:
            user_total = self._user_spend.get(user_id, 0.0)
            session_total = self._session_spend.get(session_id, 0.0)

            if user_total + cost > self.user_daily_limit:
                return False, f"Daily limit reached (${self.user_daily_limit:.2f})"
            if session_total + cost > self.session_limit:
                return False, f"Session limit reached (${self.session_limit:.2f})"

            self._user_spend[user_id] = user_total + cost
            self._session_spend[session_id] = session_total + cost
            return True, ""

    def reset_daily(self) -> None:
        with self._lock:
            self._user_spend.clear()  # must be scheduled at midnight; not automatic

budget = BudgetGuard(user_daily_limit_usd=2.0, session_limit_usd=0.50)

def budget_gated_call(messages: list, user_id: str, session_id: str) -> dict:
    # Estimate cost before calling (use input token count as proxy)
    estimated_input = sum(len(str(m)) // 4 for m in messages)
    estimated_cost = estimated_input * PRICING["claude-sonnet-4-6"]["input"] + 0.01  # rough estimate

    allowed, reason = budget.check_and_record(user_id, session_id, estimated_cost)
    if not allowed:
        return {"response": "You've reached your usage limit for today. Please try again tomorrow.", "blocked": True, "reason": reason}

    result = attributed_call(messages, feature="chat", user_id=user_id, session_id=session_id)
    return result
```

### Conversation context growth

Multi-turn conversations compound input token costs because the entire history is re-sent on every turn. Track cumulative conversation cost explicitly:

```python
def conversation_cost_analysis(turns: list[dict]) -> dict:
    cumulative_input = 0
    per_turn_costs = []

    for i, turn in enumerate(turns):
        # Input tokens include all previous turns + current turn
        context_tokens = sum(len(t["content"].split()) * 1.3 for t in turns[:i+1])
        output_tokens = len(turn.get("response", "").split()) * 1.3

        turn_cost = (
            context_tokens * PRICING["claude-sonnet-4-6"]["input"]
            + output_tokens * PRICING["claude-sonnet-4-6"]["output"]
        )
        per_turn_costs.append(round(turn_cost, 5))
        cumulative_input += context_tokens

    return {
        "per_turn_costs": per_turn_costs,
        "total_cost": round(sum(per_turn_costs), 5),
        "avg_cost_per_turn": round(sum(per_turn_costs) / len(turns), 5),
        "note": "Cost grows super-linearly with turns due to context accumulation"
    }
```

## Concrete example

A complete cost dashboard for a multi-feature AI application:

```python
import anthropic
import time
from collections import defaultdict

client = anthropic.Anthropic()

PRICING = {
    "claude-sonnet-4-6": {"input": 3.00e-6, "output": 15.00e-6},
    "claude-haiku-4-5-20251001": {"input": 0.80e-6, "output": 4.00e-6},
}

class CostDashboard:
    def __init__(self):
        self.records: list[dict] = []

    def record(self, feature: str, user_id: str, model: str, usage, cost: float):
        self.records.append({
            "timestamp": time.time(),
            "feature": feature,
            "user_id": user_id,
            "model": model,
            "input_tokens": usage.input_tokens,
            "output_tokens": usage.output_tokens,
            "cost_usd": cost,
        })

    def by_feature(self) -> dict:
        totals = defaultdict(float)
        for r in self.records:
            totals[r["feature"]] += r["cost_usd"]
        return dict(sorted(totals.items(), key=lambda x: x[1], reverse=True))

    def by_user(self) -> dict:
        totals = defaultdict(float)
        for r in self.records:
            totals[r["user_id"]] += r["cost_usd"]
        return dict(sorted(totals.items(), key=lambda x: x[1], reverse=True))

    def by_model(self) -> dict:
        totals = defaultdict(float)
        for r in self.records:
            totals[r["model"]] += r["cost_usd"]
        return dict(totals)

    def total(self) -> float:
        return sum(r["cost_usd"] for r in self.records)

    def report(self):
        print(f"Total spend: ${self.total():.4f}")
        print("\nBy feature:")
        for feature, cost in self.by_feature().items():
            pct = cost / self.total() * 100
            print(f"  {feature}: ${cost:.4f} ({pct:.0f}%)")
        print("\nTop users:")
        for user, cost in list(self.by_user().items())[:5]:
            print(f"  {user}: ${cost:.4f}")

dashboard = CostDashboard()

def tracked(feature: str, user_id: str, query: str, model: str = "claude-sonnet-4-6") -> str:
    response = client.messages.create(
        model=model,
        max_tokens=256,
        messages=[{"role": "user", "content": query}]
    )
    p = PRICING[model]
    cost = response.usage.input_tokens * p["input"] + response.usage.output_tokens * p["output"]
    dashboard.record(feature, user_id, model, response.usage, cost)
    return response.content[0].text

# Simulate mixed traffic
tracked("search", "user_a", "What is the capital of France?", model="claude-haiku-4-5-20251001")
tracked("summarize", "user_b", "Summarize the history of computing in 200 words.")
tracked("search", "user_a", "What year was the Eiffel Tower built?", model="claude-haiku-4-5-20251001")
tracked("analyze", "user_c", "Analyze the trade-offs between SQL and NoSQL databases.")

dashboard.report()
```

## When to use it / when not to

Cost tracking is not optional for production systems. The question is how granular to go:

| Stage | Minimum tracking |
|---|---|
| Prototype | Log total tokens per call; compute approximate cost |
| Beta | Tag by feature; track per-user spend; set session limits |
| Production | Full attribution (feature, user, session, model); alerting on anomalies; budget guardrails |
| Scale | Cost per successful request (not per call), percentile analysis, cost/quality trade-off dashboards |

Skip per-user tracking only if your system doesn't have identifiable users (fully anonymous, same query structure for everyone).

#### When to add budget guardrails

Add per-user guardrails when:
- Users can trigger unbounded multi-turn conversations
- You're running an agentic system where a single user action can trigger many model calls
- You're in a free-tier or freemium model where unlimited use is financially unsustainable

:::tip[My take]

The most useful single metric to track is cost per successful request — not cost per call. A pipeline with 3 model calls per user request needs to be measured as a unit. If success rate drops (more retries, more errors), cost per success goes up even if cost per call stays flat.

The per-feature breakdown is where cost tracking earns its keep. Without it, you might spend months optimizing a feature that accounts for 5% of spend while ignoring the one that accounts for 60%. Run the breakdown, find the 80/20 feature, and optimize that one first.

Conversation context growth is the cost surprise that bites the most teams. A 20-turn conversation at 200 tokens per turn isn't 4,000 input tokens — it's (200 + 400 + 600 + ... + 4,000) = 42,000 input tokens total. This super-linear growth becomes the dominant cost driver in chat applications with engaged users.

:::

## Common failure modes and gotchas

**1. Hardcoded pricing.** Model pricing changes. Hardcoded constants drift out of date within months, making your cost estimates wrong. Store pricing in config (environment variable, database row, or config file) and document when it was last updated.

**2. Not accounting for conversation context growth.** Tracking cost per turn in isolation misses the super-linear growth from re-sending history. Track cumulative cost per session, not just per call.

**3. Ignoring cache tokens.** If you use prompt caching, `cache_read_input_tokens` cost ~10% of normal input tokens. Counting them as normal input tokens makes cache cost estimates wrong. Handle each token type separately.

**4. Per-user limits without reset logic.** Daily per-user limits that don't reset at midnight accumulate indefinitely. Implement reset logic (nightly job, a TTL — time-to-live, an expiration timer — in Redis, daily bucket key).

**5. Alerting on absolute spend, not rate of change.** An alert at $1,000/day won't fire until you've already spent $1,000. Alert on rate-of-change anomalies (spend in the last hour is 3× the hourly average) for earlier detection.

**6. Not tracking failed calls.** Calls that return errors still incur input token costs (the prompt was processed before the error). Track failed call token spend separately — high error rates can make your actual cost significantly higher than successful-call cost alone.

## Project ideas

**1. Conversation cost growth visualizer** — Run a 20-turn conversation on a topic. For each turn, record the input token count from the API response. Plot cumulative input tokens vs turn number. Observe the super-linear growth. Then implement a history truncation strategy (keep last 5 turns) and compare the cost profile.

**2. Per-feature cost breakdown audit** — Instrument a multi-feature application with feature tags. Run 100 representative requests (mix of features proportional to expected production traffic). Generate the per-feature cost breakdown. Identify the most expensive feature per successful request. Document the finding.

**3. Budget guardrail stress test** — Set a session limit of $0.10. Run an automated script that makes 50 rapid model calls for the same session. Verify the guardrail triggers at the right threshold. Measure the false positive rate (legitimate sessions blocked below the limit). Tune the estimation logic.

**4. Model switch cost analysis** — Take a set of 50 real queries currently running on Sonnet. Run them on Haiku. Compare: total token cost, per-query cost distribution, and quality score (LLM-as-judge: a second model call that grades the first model's output against a rubric). Compute the cost reduction and quality delta. This is the data you need to make a routing decision.
