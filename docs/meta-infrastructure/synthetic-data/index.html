Synthetic Data

What it is​

Synthetic data is training data generated by a model rather than collected from human-produced sources. Instead of hiring annotators to label examples, you prompt a capable model to produce (input, output) pairs that represent the distribution you want a smaller or specialized model to learn.

The technique spans a spectrum: from simple generation ("produce 500 customer support questions in varied phrasings") to sophisticated bootstrap loops where a model generates, critiques, filters, and iteratively improves its own training data before any human reviews it.

The problem it solves​

Training data is the bottleneck for fine-tuning. Human annotation is slow, expensive, and requires domain expertise. Public datasets rarely match the specific task, format, or domain of your application. And labeled production data is often scarce in the early stages of a product.

Synthetic data breaks this bottleneck by making data generation cheap and scalable. A capable model can produce thousands of training examples in hours at the cost of API calls — far faster and cheaper than human annotation for many tasks. The tradeoff: synthetic data reflects the generating model's capabilities and biases, and can introduce systematic errors if not carefully filtered.

How it works under the hood​

Seed-based generation​

ToS check required

Anthropic's Terms of Service prohibit using Claude API outputs to train or fine-tune competing models. If your synthetic data pipeline generates Claude outputs and you use them to train an open model (Llama, Mistral), this may violate your provider agreement. Before running any API-based generation pipeline for training purposes, read your provider's terms carefully. As an alternative, use an open teacher model (Llama 3 70B, Mixtral) to avoid these restrictions.

Start with a small set of real examples (seeds) and prompt a model to generate variations:

import anthropic
import json

client = anthropic.Anthropic()

SEEDS = [
    {"input": "What is your return policy?", "output": "Returns are accepted within 30 days of purchase."},
    {"input": "How do I track my order?", "output": "You can track your order at acme.com/track using your order number."},
]

def generate_variations(seeds: list[dict], n_per_seed: int = 5) -> list[dict]:
    examples = []
    seed_text = "\n".join(f"Q: {s['input']}\nA: {s['output']}" for s in seeds)

    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=2048,
        messages=[{"role": "user", "content": f"""Generate {n_per_seed * len(seeds)} new customer support question-answer pairs similar in style and domain to these examples, but with different phrasings, topics, and edge cases.

Seed examples:
{seed_text}

Requirements:
- Vary the phrasing significantly (not just paraphrase)
- Include some edge cases and unusual but valid questions
- Keep answers accurate and in the same format
- Return valid JSON array: [{{"input": "...", "output": "..."}}]

Return only the JSON array, no other text."""}]
    )

    try:
        return json.loads(response.content[0].text)
    except json.JSONDecodeError:
        return []

synthetic = generate_variations(SEEDS, n_per_seed=5)
print(f"Generated {len(synthetic)} examples")
for ex in synthetic[:3]:
    print(f"Q: {ex['input']}\nA: {ex['output']}\n")

Diversity-aware generation​

Naive generation produces similar examples that cluster around common patterns. Force diversity by varying personas, scenarios, and difficulty:

DIMENSIONS = {
    "user_type": ["first-time buyer", "long-term customer", "enterprise account", "non-native English speaker"],
    "channel": ["website chat", "email", "phone call transcript"],
    "sentiment": ["neutral", "frustrated", "confused", "urgent"],
    "complexity": ["simple one-sentence question", "multi-part question", "question with incorrect assumption"],
}

def generate_diverse_batch(domain: str, n: int = 20) -> list[dict]:
    import random
    examples = []

    for _ in range(n):
        dims = {k: random.choice(v) for k, v in DIMENSIONS.items()}
        prompt = f"""Generate one realistic customer support question for a software company.

Context for this question:
- User type: {dims['user_type']}
- Channel: {dims['channel']}
- User sentiment: {dims['sentiment']}
- Question complexity: {dims['complexity']}
- Domain: {domain}

Generate the question and an ideal support agent response.
Return JSON: {{"input": "...", "output": "...", "metadata": {dims}}}"""

        response = client.messages.create(
            model="claude-haiku-4-5-20251001",
            max_tokens=256,
            messages=[{"role": "user", "content": prompt}]
        )
        try:
            examples.append(json.loads(response.content[0].text))
        except json.JSONDecodeError:
            continue

    return examples

diverse_batch = generate_diverse_batch("SaaS billing and subscription management", n=10)

Quality filtering​

Not all generated examples are good. Filter before using for training.

A note on circular validation: using a smaller model (Haiku) to judge outputs from a larger model (Sonnet) is unreliable — the smaller model cannot consistently assess quality it cannot produce. The filter below works as a coarse signal, but calibrate it manually: sample 50–100 generated examples, score them yourself, and check how often the filter agrees. If precision is below 80%, either raise the threshold or replace the LLM judge with a task-specific rubric.

def quality_filter(examples: list[dict], threshold: float = 0.7) -> list[dict]:
    passing = []

    for example in examples:
        # 1. Length checks
        if len(example.get("input", "")) < 10:
            continue
        if len(example.get("output", "")) < 20:
            continue

        # 2. LLM-as-judge quality check
        judge_response = client.messages.create(
            model="claude-haiku-4-5-20251001",
            max_tokens=64,
            messages=[{"role": "user", "content": f"""Rate the quality of this Q&A pair for a customer support training dataset.

Q: {example['input']}
A: {example['output']}

Score 0.0-1.0 on: relevance, answer accuracy, natural language quality, usefulness.
JSON only: {{"score": 0.0-1.0, "reason": "one phrase"}}"""}]
        )
        try:
            rating = json.loads(judge_response.content[0].text)
            if rating["score"] >= threshold:
                example["quality_score"] = rating["score"]
                passing.append(example)
        except (json.JSONDecodeError, KeyError):
            continue

    return passing

filtered = quality_filter(synthetic, threshold=0.7)
print(f"Retained {len(filtered)}/{len(synthetic)} examples after quality filtering")

Bootstrap loops (self-improvement)​

A model generates data, critiques it, rewrites failures, and iterates — producing progressively better training data without human intervention:

def bootstrap_loop(task_description: str, n_rounds: int = 3, examples_per_round: int = 20) -> list[dict]:
    all_examples = []

    for round_num in range(n_rounds):
        # Generate
        generate_prompt = f"""Generate {examples_per_round} training examples for: {task_description}

Format: JSON array of {{"input": "...", "output": "..."}}
{"Previous round produced " + str(len(all_examples)) + " examples. Generate diverse new ones." if round_num > 0 else ""}"""

        gen_response = client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=4096,
            messages=[{"role": "user", "content": generate_prompt}]
        )

        try:
            new_examples = json.loads(gen_response.content[0].text)
        except json.JSONDecodeError:
            continue

        # Filter and critique
        quality_passed = quality_filter(new_examples, threshold=0.75)

        # Add to pool
        all_examples.extend(quality_passed)
        print(f"Round {round_num + 1}: generated {len(new_examples)}, kept {len(quality_passed)}")

    return all_examples

Deduplication​

Generated datasets often contain near-duplicate examples. Deduplicate before training:

from sentence_transformers import SentenceTransformer
import numpy as np

def deduplicate(examples: list[dict], similarity_threshold: float = 0.92) -> list[dict]:
    model = SentenceTransformer("BAAI/bge-small-en-v1.5")
    inputs = [ex["input"] for ex in examples]
    embeddings = model.encode(inputs, normalize_embeddings=True)

    keep = [0]  # always keep first
    for i in range(1, len(embeddings)):
        similarities = embeddings[keep] @ embeddings[i]
        if similarities.max() < similarity_threshold:
            keep.append(i)

    return [examples[i] for i in keep]

deduped = deduplicate(filtered)
print(f"After deduplication: {len(deduped)}/{len(filtered)} examples")

Concrete example​

A complete pipeline that generates, filters, deduplicates, and exports a fine-tuning dataset for a classification task:

import anthropic
import json
from sentence_transformers import SentenceTransformer
import numpy as np

client = anthropic.Anthropic()
embed_model = SentenceTransformer("BAAI/bge-small-en-v1.5")

CATEGORIES = ["billing", "technical_support", "account_management", "shipping", "general_inquiry"]

def generate_classification_data(n: int = 100) -> list[dict]:
    examples = []
    per_category = n // len(CATEGORIES)

    for category in CATEGORIES:
        response = client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=2048,
            messages=[{"role": "user", "content": f"""Generate {per_category} realistic customer support messages that belong to the '{category}' category.

Vary: length (1–4 sentences), formality, level of detail, and customer frustration level.
Return JSON array: [{{"text": "...", "label": "{category}"}}]
Only JSON, no other text."""}]
        )
        try:
            batch = json.loads(response.content[0].text)
            examples.extend(batch)
        except json.JSONDecodeError:
            pass

    return examples

def filter_and_dedup(examples: list[dict], min_length: int = 15) -> list[dict]:
    # Length filter
    examples = [e for e in examples if len(e.get("text", "")) >= min_length]

    # Deduplication
    texts = [e["text"] for e in examples]
    embeddings = embed_model.encode(texts, normalize_embeddings=True)
    keep = [0]
    for i in range(1, len(embeddings)):
        sims = embeddings[keep] @ embeddings[i]
        if sims.max() < 0.90:
            keep.append(i)

    return [examples[i] for i in keep]

def export_for_finetuning(examples: list[dict], path: str) -> None:
    with open(path, "w") as f:
        for ex in examples:
            record = {"messages": [
                {"role": "user", "content": f"Classify this customer message: {ex['text']}"},
                {"role": "assistant", "content": ex["label"]}
            ]}
            f.write(json.dumps(record) + "\n")

raw = generate_classification_data(n=100)
print(f"Generated: {len(raw)}")
clean = filter_and_dedup(raw)
print(f"After filter+dedup: {len(clean)}")
export_for_finetuning(clean, "classification_training.jsonl")
print("Exported to classification_training.jsonl")

# Category balance check
from collections import Counter
label_counts = Counter(ex["label"] for ex in clean)
print("Distribution:", dict(label_counts))

When to use it / when not to​

Synthetic data is appropriate when​

  • You need to fine-tune for a specific task and labeled data is scarce or expensive
  • Your task distribution is well-defined (classification, extraction, a specific response format)
  • You have a capable model to generate from and a quality filtering mechanism
  • You're augmenting a small real dataset, not replacing real data entirely

Prefer real data when​

  • Accuracy of edge cases matters — synthetic data underrepresents tail behaviors
  • The task requires knowledge the generating model doesn't have (recent events, proprietary information)
  • You're in a regulated domain where training data provenance must be documented
  • You need to represent the actual distribution of real user inputs, not a model's approximation of it

The practical question​

Can you define what a good training example looks like well enough to prompt a model to produce one? If yes, synthetic data is viable. If the task requires nuanced human judgment or domain knowledge the model lacks, generating quality examples will be difficult.

My take

Quality filtering is where most synthetic data pipelines fail or succeed. Generate 2× what you need, filter aggressively, and use only the high-confidence examples. A smaller high-quality dataset trains a better model than a large noisy one — every garbage example teaches the model something wrong.

The diversity problem is subtle. Naive generation produces examples that cluster around the most common patterns. Use the dimension-based approach (vary user type, sentiment, complexity) to force coverage of edge cases. Then check your generated dataset: embed all examples and look for clusters. If you have 10 examples within cosine distance 0.05 of each other, you've overrepresented that part of the distribution.

Always mix at least some real data in. Purely synthetic fine-tuning can produce a model that sounds like the generating model — missing the natural variation, the weird phrasings, the errors and corrections that appear in real human-produced data. Even 10–20% real examples in the training mix helps the student generalize better.

Common failure modes and gotchas​

1. Model-generated bias amplification. Synthetic data inherits the generating model's biases. If the teacher model has a bias (favoring certain phrasings, avoiding certain topics), the student trained on its outputs amplifies that bias. Audit your generated dataset for systematic patterns before training.

2. Distribution mismatch with production. Generating "plausible" customer questions is different from generating the actual questions your users ask. Real users write with typos, mixed languages, incomplete sentences, and implicit context. Include realistic noise in generation prompts, and validate that the synthetic distribution matches a sample of real traffic.

3. Using all generated data without filtering. LLMs make mistakes. Some generated examples will be wrong, inconsistent, or low-quality. Always run quality filtering before training. A model trained on 5% garbage examples learns to produce garbage 5% of the time.

4. Legal and ToS issues. Some model providers restrict using API outputs to train competing models. Check your provider's terms before building a distillation or synthetic data pipeline that will train another model.

5. No holdout of real data for evaluation. Evaluating a synthetic-data-trained model on synthetic-data-generated eval examples doesn't tell you how it performs on real inputs. Always hold out some real labeled examples (even 50–100) for a realistic evaluation of the trained model.

6. Forgetting to check label balance. Generation prompts that don't specify balance will produce skewed datasets — common categories get more examples than rare ones. Check label distribution and either re-generate to balance or use loss weighting during training.

Project ideas​

1. Full synthetic fine-tuning pipeline — Pick a classification task (topic detection, sentiment, intent). Generate 1,000 examples using the teacher model. Filter by quality score. Fine-tune a 3B model using LoRA. Evaluate on 100 real labeled examples. Compare: synthetic-trained model vs. teacher on accuracy, latency, and cost.

2. Diversity analysis — Generate 500 synthetic examples without diversity constraints and 500 with the dimension-based approach. Embed all examples. Visualize the embedding space (UMAP or t-SNE). Measure cluster sizes and coverage. Show whether dimension-based generation produces better-distributed training data.

3. Quality filter calibration — Generate 200 examples for a task you can evaluate manually. Score all 200 examples yourself (good/bad). Run the LLM-as-judge filter at thresholds 0.5, 0.7, 0.8, 0.9. Measure precision and recall of the filter against your manual labels at each threshold.

4. Synthetic + real data mixing — Fine-tune a model on: (a) 100% synthetic data, (b) 80% synthetic + 20% real, (c) 100% real. Measure accuracy on a real test set. Quantify the benefit of mixing real data into a synthetic training set.

Going deeper​

Foundational reading​

  • Wang et al., "Self-Instruct: Aligning Language Models with Self-Generated Instructions" (2023) — the bootstrap loop approach; how models can generate their own instruction-following training data.
  • Gunasekar et al., "Textbooks Are All You Need" (2023) — synthetic "textbook" data used to train small models; shows that data quality matters more than data quantity.
  • Chen et al., "Alpaca: A Strong, Replicable Instruction-Following Model" (Stanford, 2023) — fine-tuning Llama on GPT-4-generated instruction data; one of the first widely-used distillation-via-synthetic-data results.

Libraries​

  • trl documentation — SFTTrainer for training on synthetic data; RLHF tools for synthetic preference data.
  • Argilla (argilla.io) — platform for reviewing and correcting synthetic data with human annotators; useful for closing the loop on quality issues.
