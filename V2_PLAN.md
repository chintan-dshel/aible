## 3. (b) Chapter outline

### Front matter

**Start Here** (rewrite of `intro.md`). What this book is, who it is for, how Parts 1–3 relate, two reading paths (patterns-first, teardowns-first). One diagram: the map of the book.

### Part 1 — Ground rules of agentic system design

Each chapter follows one fixed shape, deliberately different from the v1 9-section template:

1. **The problem in one diagram** — the failure you get without the pattern
2. **The pattern** — one or two diagrams plus mechanism
3. **Decision rules** — use when / don't use when, stated as tests you can apply
4. **Where it shows up in the teardowns** — forward links into Part 2 with one line each
5. **Failure modes** — what goes wrong when you apply the pattern badly
6. **Reference material** — the v1 pages mapped to this chapter, with one line on what to read each for

Target length 1,200–1,800 words plus 2–4 diagrams. Prose stays below the diagrams.

| # | Chapter | Summary |
|---|---|---|
| 1 | **Orchestration vs. autonomy** | The spectrum from a fixed workflow that calls models at known points, to an agent loop that decides its own next step. Most production systems should sit nearer the orchestrated end; autonomy is bought with unbounded cost and unbounded behaviour. |
| 2 | **Stage gates** | A gate is a checkpoint between phases where output is validated (by rules, a judge, or a human) before the next phase spends money or takes an irreversible action. The gate is the unit of control in every system in Part 2. |
| 3 | **State machines** | Model the pipeline as explicit states and transitions so "where are we" is a stored fact, not something inferred from chat history. This is what makes runs resumable, observable, and auditable. |
| 4 | **QA pipelines** | Draft → review → revise loops, parallel reviewers with non-overlapping lenses, and a human gate that stops reviewers from over-flagging. When to stop iterating. |
| 5 | **LLM-as-judge** | Using a model to score another model's output. Rubric design, calibrating the judge against human labels, why judge and target should differ, and how a judge can be gamed. |
| 6 | **Cost-aware model routing** | Assigning model tiers per stage or per task, spending caps, fallback chains, and attributing cost per agent so you know which stage is expensive. |
| 7 | **Memory layers** | In-context, session, persistent store, and retrieval — what each agent should and should not remember, and how memory becomes an attack surface (poisoning, cross-user leakage). |
| 8 | **Failure modes and attack surfaces** | Prompt injection (direct and indirect), tool misuse, runaway loops, error propagation between agents. Where in the diagrams from chapters 1–7 each defence sits. |
